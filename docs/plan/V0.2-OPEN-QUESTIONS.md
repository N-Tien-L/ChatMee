## A. Decisions that block M1 release

These do not block the agreed local harness/recovery/unread planning. Resolve before calling a candidate release-ready. They do not reopen the two choices above.

### OQ-01: Are the documented v0 security/privacy gaps acceptable for the M1 release audience?

- Options: (A) retain the current Approved v0 deferrals for a limited hobby/demo audience with explicit limitations; (B) require a separately specified security/privacy milestone before M1 release.
- Recommendation: A for the stated low-cost scope, subject to explicit owner acceptance of the audience and residual risk. Keep server-side WS logout/session-expiry revocation, unused token revocation and global presence visible in release notes. Do not infer acceptance for wider/public usage from this recommendation.
- Impact: B changes scope and release order. It needs an owner-approved amendment to SPEC-008 section 2 and, for presence visibility, the SPEC-005 AC-005-4 design before coding. A does not make existing sockets invalid after logout and does not restrict global presence.
- Decision: Pending.

### OQ-02: What release lineage and label should M1 use?

- Options: (A) confirm and close the remaining v0.1 sign-off actions, then version M1 as the next release; (B) retain a prerelease/candidate label until v0.1 deployment, rotation/backfill status and tag history are confirmed.
- Recommendation: B until the owner confirms the facts/actions, then A if appropriate. The planning name “v0.2 M1” is not a tag instruction.
- Impact: avoids claiming v0.1 was released based on feature code or the old brief. Existing records still show an Unreleased changelog and historical pending owner actions; this audit did not inspect production or perform those actions.
- Decision: Pending. Owner confirmation must not include secrets; a status and revision reference are sufficient.

### OQ-03: Who performs the real OAuth/mobile release smoke, and when?

- Options: (A) owner performs the two-account Google/GitHub and mobile-browser smoke after automated candidate gates; (B) owner names a trusted tester and supplies access outside committed artifacts.
- Recommendation: A on the candidate revision, before release operations. Reuse the agreed workflow rather than storing browser sessions or provider credentials in CI.
- Impact: fixture OAuth does not validate the deployed provider callback/client configuration or actual mobile keyboard behavior. Without a named operator and a recorded result, CM-099 remains unready. A production smoke, if later authorized, is an owner action; this task does not call production.
- Decision: Pending operator/date; the real-smoke requirement itself was already selected.

## B. Decisions that can wait until after M1

### OQ-04: Where should per-room drafts live, and for how long?

- Options: (A) tab-scoped `sessionStorage`; (B) `localStorage` surviving browser restarts; (C) memory only, surviving room switches but not reload.
- Recommendation: A, account/room namespace, text only, clear after successful send, confirmed logout and room-access loss. Proposed expiry: 24 hours after the last draft update; owner must approve this duration and whether an expired login clears drafts before reauthentication.
- Impact: A limits persistence and needs no server service but does not sync tabs/devices. B retains private text longer on shared devices and requires stronger account-switch/expiry rules. C has less retention risk but loses reload continuity.
- Decision: Pending. M2 spec approval required; the proposed duration is not an approved retention policy.

### OQ-05: Which optional milestone should follow M1, and must they share one version?

- Options: (A) approve and release M2 drafts, then M3 reply, with M4 reactions evaluated later; (B) prioritize M3 reply next; (C) stop v0.2 after M1 and reassess from user feedback.
- Recommendation: A only if M1 is stable and the owner wants another increment; every milestone remains independently releasable. C is a valid low-cost endpoint.
- Impact: B adds API/data/permission work earlier. Grouping all candidates under one release delays useful stabilization and creates more integration risk. No optional milestone is authorized for coding by this plan.
- Decision: Pending.

### OQ-06: What edit/unsend windows and history retention are acceptable?

- Options: (A) bounded edit/unsend windows with no user-visible revision history; (B) bounded windows plus retained revisions under an owner-approved access/retention policy; (C) defer lifecycle mutations.
- Recommendation: C for v0.2's first release. Before any later implementation, choose exact edit and unsend durations separately and decide whether old content is retained, who can read it, and when it is removed. Do not silently retain hidden revision copies under option A.
- Impact: retention affects privacy, moderation evidence, storage and account-deletion expectations. Unsend must define quote/search/preview/report handling and cannot revoke content already seen or copied. Administrator deletion is a separate right, not implied by own-message editing.
- Decision: Pending; no time window or retention default is approved.

### OQ-07: Should delete-for-me follow the account across devices?

- Options: (A) server-side per-user hidden-message records; (B) device-local hiding only; (C) defer.
- Recommendation: A if the feature is selected later; keep C for M1. Do not reuse shared `Message.isDeleted` for a per-user action.
- Impact: A needs a model/index and filtering rules for history, search and quote context. B is cheaper but messages reappear on other devices or local data reset, which must be explained to users. Both need a policy for previews/unread and restore behavior.
- Decision: Pending.

### OQ-08: What attachment scope and spending ceiling are acceptable?

- Options: (A) image-only pilot with a strict storage/egress quota and approved validation/quarantine policy; (B) images plus general files with scan/download policy; (C) defer uploads.
- Recommendation: C until M1 is stable, then A if the owner approves a concrete monthly currency amount, per-file size, per-user quota, retention and moderation policy. No paid service or provider is selected here.
- Impact: B expands malware/MIME handling and support burden. Even an image-only pilot needs private object access, orphan cleanup and cost enforcement. Public URLs and Render local files are not an acceptable implicit storage policy.
- Decision: Pending scope and numeric budget/limits; no spending authorization.

### OQ-09: What privacy default should read receipts and push use?

- Options: (A) opt-in for receipts and push, generic notification text by default; (B) receipts on by default, push opt-in; (C) defer both.
- Recommendation: C for M1 and A if later selected. Decide separately whether a notification may include sender/message preview on a locked device.
- Impact: read receipts disclose activity and require a new validated marker model. Push exposes information outside the app and requires subscriptions, delivery/retry/revocation handling and a background-delivery assessment. A sender's server echo must not be relabeled as recipient delivery/read proof.
- Decision: Pending; no receipt or notification default is approved.

### OQ-10: Which later interruption/navigation problem matters most?

- Options: (A) room-scoped text search first; (B) notification controls/mute first, followed by mentions; (C) collect usage feedback before selecting any.
- Recommendation: C after the M1 release. If unwanted interruptions already dominate owner feedback, select B before adding mentions or push.
- Impact: A needs scoped search and jump context with lifecycle filtering. B needs clear muted badge/title/in-app/push semantics and an amendment to SPEC-009 AC-009-27. Mentions without controls add interruption and privacy obligations rather than completing M1.
- Decision: Pending.
