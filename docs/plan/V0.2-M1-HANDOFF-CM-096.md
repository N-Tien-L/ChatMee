## Implementation

- One session ledger holds at most **512** `(roomId, messageId)` keys across all
  rooms. A repeated retained ID or the current summary ID cannot increment again.
  The ledger is discarded on account change and cache clearing, including logout
  during loading followed by login to the same account.
- Unknown older/tied activity, invalid ordering data and an evicted old ID do not
  guess an unread increment. They trigger a coalesced authoritative `GET /rooms`.
  Newer activity updates the summary/count immediately; older activity cannot move
  the summary backwards. Equal timestamps are uncertain and reconciled by server.
- Read requests are serialized per room. Concurrent requests for the same head
  share work; activity during a visible read queues one trailing read for the newer
  head. Hiding the tab or switching rooms prevents that trailing automatic read.
- A failed optimistic read keeps a retry requirement and refreshes authoritative
  unread. If the server is unreachable, the requirement survives until another
  open/visible activity/reconnect attempt. There is no timer/polling retry loop.
  Reconnect refresh marks the visible open room using existing read-at-now semantics.
- Room-list requests share one in-flight operation. A revision watermark changes
  on activity, lifecycle changes and read starts/completions. Responses from an
  earlier revision are discarded and fetched again, at most **three** requests per
  operation. Continuous contention exposes the existing Retry UI instead of
  publishing a known stale snapshot or polling indefinitely.
- Pending reads preserve local unread across snapshots; success with intervening
  hidden activity and failure both reconcile with the server. List snapshots retain
  a newer local summary while accepting server unread. Old-account responses cannot
  publish, and failed-read entries are pruned when authoritative rooms disappear.
- Unversioned room snapshots preserve existing unread until a guarded refetch resolves
  a conflict. They cannot resurrect an ended/hidden room. Explicit ROOM_ADDED,
  legitimate unknown-room activity (including DM unhide), create/open responses and
  authoritative list snapshots can restore the room. Activity bursts during an
  unknown-room GET cause a subsequent list reconciliation.
- Existing title and sorting consume the reconciled store. No production UI component
  change was needed. Own messages do not increment; SYSTEM/deleted exclusions remain
  enforced by the unchanged backend activity/query contract.

## Limits and follow-ups

- Read marker still means server **now**, not the latest loaded/visible history row.
  No read receipts, viewport reads, mark-as-unread, new event, polling or backend
  production change was introduced. Multi-page recovery behavior remains CM-095's.
- No immediate cross-tab read notification exists. Other sessions converge on their
  next reconnect/refetch, not an invented read event. Offline/5xx reads retain retry
  intent; closed or hidden rooms are reconciled without automatically reading unseen messages.
- Three consecutive raced snapshots preserve local activity and expose Retry. Successful
  authoritative reconciliation requires a reachable server and a quiet-enough request
  interval. This is a bounded retry/error path, not durable event replay.
- The existing single-instance app timestamp ordering and read-at-now late-write limits
  remain. A stronger sequence/replay/read-receipt contract requires a separate spec.
- CM-094/095 full-stack acceptance remains blocked together with CM-096. No claim of
  release readiness or real-provider/mobile verification follows from unit/build passes.
